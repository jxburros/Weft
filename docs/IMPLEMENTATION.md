# Implementation coverage

This document compares the repository with **AI Workspace Browser Product Specification v1.0**. The specification is broader than the current application. This build is a working Electron workspace browser with local persistence, shared automation commands, reference captures, and text model connections. It is **not a completed implementation of every product requirement**, a protected credential broker, or an autonomous agent runtime.

Status terms below: **Implemented** means the described bounded behavior exists; **Partial** means part of the section exists with listed gaps; **Not implemented** means the capability is unavailable. Presence in the product specification does not imply a shipped feature.

## Architecture and actual boundaries

- Electron/Chromium renders remote pages in sandboxed `WebContentsView` instances with Node integration disabled and context isolation enabled. The trusted application renderer has a narrow preload API, sender/frame checks, and no direct Node integration.
- Workspaces use separate persistent Chromium session partitions. Switching a tab's workspace opens a fresh page in the destination partition; it does not transfer session credentials or live JavaScript state.
- `commands.js`, `workspace-commands.js`, and `provider-commands.js` define validated commands shared by GUI, CLI, MCP, and REST. Every command carries an action class, resource, data classes, effect and sensitive outbound categories. The shared dispatcher passes every non-human command (bootstrap token, scoped clients, CLI/MCP/REST, in-process callers and the internal model read tools) through one authority gate before any handler runs: human-only floors, client grants (purpose, workspaces with explicit cross-workspace grants, read/record/tab scopes, extra action classes, data classes, destination origin patterns, usage/rate limits, task binding, expiry, revocation), autonomy levels with per-workspace ceilings, and a single durable approval queue resolved only in the trusted GUI. See [ADR-005](decisions/005-agent-authority-and-audit.md). The bootstrap token defaults to the `autonomous` level for compatibility; the human can lower it.
- Browser tools can inspect pages and run JavaScript. They must be treated as powerful account access when an authenticated page is open. Denying raw cookie commands to automation does **not** make DOM, evaluation, screenshots, or authenticated-account activity secret-safe.
- Built-in model chat streams replies from the selected endpoint (OpenAI-compatible, Anthropic or Ollama native) and sends only the new message, retained history and attachments the user selected and reviewed item by item. Images are sent only as bounded PNG bytes to connections configured or probed as image-capable, or to a human-configured vision fallback after per-turn acknowledgement. Optional OpenAI-compatible read-only tools require model capability plus explicit request consent, are scoped to the conversation workspace and selected tab, and are limited to five calls. Chat cannot interact with pages, execute workflows or run autonomous tasks. Cloud inference occurs at the selected remote provider; local connection failures never select another provider.
- Plugins (`src/plugins/`) contribute formats, extractors, reports, an after-command observer and read-only commands through five named hooks invoked only by the registry. Built-ins are reviewed modules; third-party plugins in `<user data>/plugins` are listed without running code, enabled only by a person against manifest/code digests, never run for automation unless allowed, and execute in a per-plugin child process (Node permission model, empty environment, `vm` context without Node/network/code generation, 2 s/8 MiB/64 MiB limits). Every plugin command, `plugins.invoke` (raised to the operation's manifest-derived class) and each nested read a plugin or hook makes passes the shared authority gate with the caller's identity, approvals and activity logging. An import-boundary test enforces that core does not import plugin modules.
- Browser extensions are per-workspace unpacked Manifest V3 packages managed only from the trusted interface. Hostile or unverified permissions are refused at audit; enabled extensions load only into their workspace partition, and extension-originated requests are limited to granted hosts and every block rule. Emergency stop terminates plugin processes as well as model streams. An enabled extension still runs code in matching pages and can read what they show.
- The OS may protect saved model keys through Electron `safeStorage`. The app rejects plaintext fallback storage for keys and also supports named environment variables. This protects stored keys under the OS's assumptions; it does not isolate them from an attacker controlling the host or app process.

## Data handling and recovery limits

Project state is stored in `workspace-data/workspace-state.json` beneath Electron's user-data directory. Model connection metadata and encrypted key blobs use a separate file. Chromium session data resides in its own partition storage. Browser security state uses separate small files beside the project store: `temporary-storage-journal.json` (origins to erase), `threat-intel.json` (installed lists and provider state; no API key) and `download-safety.json` (scanner configuration). Storage modes are kept in the project store but excluded from exports. Project JSON and captures are **not encrypted at rest**. Files are written with restrictive requested permissions where supported, but host filesystem/OS permissions remain relevant.

The supported project store limit is 100 MiB; each stored material is limited to 10 MiB and each PNG capture to 20 MiB. The GUI importer currently accepts exports below 50 MiB, and REST requests are capped at 1 MiB. Large project/file operations therefore are not interchangeable across every transport. The entire JSON store is rewritten for persistence and is not suitable for large research archives or concurrent independent writer processes.

Export excludes configured provider keys, Chromium sessions/cookies, model settings, and global site rules. URL metadata removes known sensitive parameter names and fragments. This is not comprehensive secret detection: user-authored notes, URL path segments, ordinary query values, copied files, transcripts, and screenshots may contain sensitive information. Inspect exported content before sharing it. Optional exact-term residue scanning reports found/clean/unverifiable and treats PNGs/unsupported binary formats as unverifiable; it is not automatic redaction. See [local storage and export safety](STORAGE-SAFETY.md) for lock recovery, schema upgrades, conflict warnings, and tested limits.

An import never writes a path from its input. Stored file names are reduced to basenames; source HTML is retained as plain text; PNG base64 is normalized. Import rejects malformed supported fields and rolls back project state on failure. It creates new IDs and resets site rules/workflows to inactive. Project duplication uses the same import pathway. Manual exports are the available backup mechanism; scheduled backups and verified disaster recovery are not provided; schema upgrades do automatically preserve the original file. On an unreadable or unsupported state file, preserve the original before attempting recovery.

## Validation

- `test/storage-safety.test.js`: cross-process locking, external changes, write verification, version migrations/backups, secret-field rejection, export residue outcomes and preserved sync conflicts.

- `test/workspace.test.js`: persistence/revisions, scope and administration checks, archive/delete continuity, exact artifact versions/hashes, invalid image rejection and normalization, rule boundaries/precedence, disabled imported policy/workflow records, import rollback and secret-field exclusion, preservation of corrupt state.

## Distribution and updates

Policy: [ADR-010](decisions/010-distribution-and-updates.md); procedure, trust roots and support policy: [RELEASING.md](RELEASING.md).

- **Packaging:** `electron-builder.config.cjs` builds Windows NSIS x64, macOS dmg/zip (arm64, x64) and Linux AppImage/deb (x64). The Windows installer is assisted, per-user by default, with generated brand bitmaps (`scripts/generate-installer-art.js`, checked byte-for-byte by tests) and `packaging/installer.nsh` text. Upgrades never touch user data; uninstall keeps the `weft` profile unless the person ticks and confirms deletion. Packaged builds pin the profile folder to `appData/weft`, the same as source runs. Verified: Linux AppImage/deb build, packaged AppImage launch smoke test; NSIS installer and uninstaller scripts compile with makensis on Linux. Not verified: running the Windows installer, macOS builds, signing/notarization.
- **Updater (`src/updater.js`):** `update.status` (local read; also available to scoped read clients) and human-only `update.check`, `update.install`, `update.rollback`, `update.configure` in the shared catalog; GUI Settings > Updates shows version, channel, install type, kill switch, last check, staged update, verification and signature status, health and rollback. Requests go only to the compiled `jxburros/Weft` releases URL and allowlisted GitHub release hosts through a cookie-less Electron session; the manifest must be strict electron-builder `latest*.yml`, stable, newer, and match its release tag. Files are size/SHA-512-verified while streaming and again before install; Windows pins the Authenticode publisher of a signed installation. Background checks are off by default, at most daily and only stage. Source runs have no transport; `WEFT_DISABLE_UPDATES` stops all update traffic and installs.
- **Activation and rollback:** Windows hands off to the visible installer (`--updated`); AppImage is replaced by copy-verify-rename and relaunched; macOS dmg and `.deb` are opened for a visible manual install and reported as `handed_off_manual`. The new version must pass a health check (GUI loaded, API listening, store open) within two launches; otherwise it is marked failed, AppImage restores the retained previous file automatically, Windows offers a retained verified previous installer when one exists, and other platforms show manual guidance. A crash before Weft's JavaScript starts cannot be detected directly.

## API contract and live events

Authenticated `GET /v1/openapi.json` publishes an OpenAPI 3.1 document generated from every canonical command's JSON schema. `POST /v1/execute` uses a discriminated command envelope; the published alternatives preserve each command's input requirements. Human-only operations remain listed for discovery but cannot be authorized by an automation token. Gate refusals return 403 with `error.details.authority`; approval requests return 403 `approval_required` (CLI exit 5) with an `approvalId`.

Authenticated `GET /v1/events` provides live server-sent events. Supply the bearer token in the HTTP authorization header; URL tokens and browser-origin EventSource access are unsupported. Events use a strict metadata allowlist: event type, known command, human/automation/scoped-client actor, success/failure, stable workspace/target IDs, tab ID, and state version. They do not contain command arguments, results, errors, page URLs/titles, provider messages, or screenshots. Gate refusals and approval requests appear with status `blocked`. The event stream is not an audit transcript (use `activity.list`) or proof of an external action's success. Scoped clients receive only authorized workspace events; expiry/revocation ends streams. Each event has an SSE id; reconnecting with `Last-Event-ID` replays retained later events (in memory only: 1,000 events, 1 MiB, 15 minutes) under the same allowlist and scope, preceded by an `event: gap` frame when events expired, the process restarted or the id is unknown. Consumers should read current state after a gap. Model turn progress uses separate authenticated turn streams documented in [agent integration](AGENT-INTEGRATION.md).

The server limits concurrent event subscribers to 16, emits heartbeat comments, disconnects slow consumers, and unsubscribes closed connections. When the server is used without a shared application subscription callback, only commands executed through that server produce events.
