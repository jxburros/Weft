# Implementation coverage

Last verified against code: 2026-10-18.

This document compares the repository with **AI Workspace Browser Product Specification v1.0**. The specification is broader than the current application. This build is a working Electron workspace browser with local persistence, shared automation commands, reference captures, and text model connections. It is **not a completed implementation of every product requirement** or a hosted, unattended agent service: the durable task runtime runs plans only at a person-chosen autonomy level through the same authority gate. It includes a credential broker with protected login operations ([ADR-017](decisions/017-credential-broker-and-protected-login.md)) that has been adversarially tested but **not independently security-reviewed**, so credential isolation is not asserted, and payment authorization bound to checkout terms ([ADR-019](decisions/019-payment-authorization.md)) that has **not been validated with real merchants, processors or card-issuer accounts**.

Status terms below: **Implemented** means the described bounded behavior exists; **Partial** means part of the section exists with listed gaps; **Not implemented** means the capability is unavailable. Presence in the product specification does not imply a shipped feature.

## At a glance

**Solid and tested:** workspaces and their records, tab ownership and takeover, the
shared command catalog across GUI, CLI, MCP and REST, offline captures, model
connections, site rules and storage controls, and the activity log.

**Working, with known gaps:** the authority and approval model, credential
brokerage, payment authorization, community lists, accessibility, updates and
distribution. Most of these are tested with fixtures or offscreen Chromium, not
with real accounts, merchants, assistive technology or signed installers.

**Not built:** synchronization, collaboration and any hosted service
([ADR-002](decisions/002-sync-collaboration-remote.md)).

The sections below give exact boundaries. Read the summary table first, then the
detail for the area you care about.

## Architecture and actual boundaries

- Electron/Chromium renders remote pages in sandboxed `WebContentsView` instances with Node integration disabled and context isolation enabled. The trusted application renderer has a narrow preload API, sender/frame checks, and no direct Node integration.
- Workspaces use separate persistent Chromium session partitions. Switching a tab's workspace opens a fresh page in the destination partition; it does not transfer session credentials or live JavaScript state.
- `commands.js`, `workspace-commands.js`, and `provider-commands.js` define validated commands shared by GUI, CLI, MCP, and REST. Every command carries an action class, resource, data classes, effect and sensitive outbound categories. The shared dispatcher passes every non-human command (bootstrap token, scoped clients, CLI/MCP/REST, in-process callers and the internal model read tools) through one authority gate before any handler runs: human-only floors, client grants (purpose, workspaces with explicit cross-workspace grants, read/record/tab scopes, extra action classes, data classes, destination origin patterns, usage/rate limits, task binding, expiry, revocation), autonomy levels with per-workspace ceilings, and a single durable approval queue resolved only in the trusted GUI. See [ADR-005](decisions/005-agent-authority-and-audit.md). The bootstrap token defaults to the `autonomous` level for compatibility; the human can lower it.
- Browser tools can inspect pages and run JavaScript. They must be treated as powerful account access when an authenticated page is open. Denying raw cookie commands to automation does **not** make DOM, evaluation, screenshots, or authenticated-account activity secret-safe. Brokered sign-in (`credentials.fill`) keeps the password itself out of agent-visible channels (see below), but an agent that can sign in still acts with that account's access afterwards.
- Built-in model chat streams replies from the selected endpoint (OpenAI-compatible, Anthropic or Ollama native) and sends only the new message, retained history and attachments the user selected and reviewed item by item. Images are sent only as bounded PNG bytes to connections configured or probed as image-capable, or to a human-configured vision fallback after per-turn acknowledgement. Optional OpenAI-compatible read-only tools require model capability plus explicit request consent, are scoped to the conversation workspace and selected tab, and are limited to five calls. Chat cannot interact with pages; with tools enabled it may only propose a task (`propose_task`), which a person reviews before anything is created or started. Cloud inference occurs at the selected remote provider; local connection failures never select another provider.
- Plugins (`src/plugins/`) contribute formats, extractors, reports, an after-command observer and read-only commands through five named hooks invoked only by the registry. Built-ins are reviewed modules; third-party plugins in `<user data>/plugins` are listed without running code, enabled only by a person against manifest/code digests, never run for automation unless allowed, and execute in a per-plugin child process (Node permission model, empty environment, `vm` context without Node/network/code generation, 2 s/8 MiB/64 MiB limits). Every plugin command, `plugins.invoke` (raised to the operation's manifest-derived class) and each nested read a plugin or hook makes passes the shared authority gate with the caller's identity, approvals and activity logging. An import-boundary test enforces that core does not import plugin modules.
- Browser extensions are per-workspace unpacked Manifest V3 packages managed only from the trusted interface. Hostile or unverified permissions are refused at audit; enabled extensions load only into their workspace partition, and extension-originated requests are limited to granted hosts and every block rule. Emergency stop terminates plugin processes as well as model streams. An enabled extension still runs code in matching pages and can read what they show.
- The OS may protect saved model keys through Electron `safeStorage`. The app rejects plaintext fallback storage for keys and also supports named environment variables. This protects stored keys under the OS's assumptions; it does not isolate them from an attacker controlling the host or app process.
- Credential broker ([ADR-017](decisions/017-credential-broker-and-protected-login.md)): website sign-ins are stored as purpose-bound references (label, purpose, exact authorized origins, optional embedded-frame origins, expiry, revocation, masked account identifier) created only in the trusted GUI, with the secret typed into a separate browser-owned window. A separate broker OS process (empty environment; Node permission model limited to `<profile>/credentials/vault`) seals each entry with AES-256-GCM under a data key wrapped by `safeStorage`, authenticating the authorization metadata; Linux `basic_text` or unavailable encryption is refused. An optional 1Password CLI adapter (`op read`) is tested only with a fake CLI. `credentials.fill` (`credential_use`: an exact one-time approval bound to the destination, or a human task grant) verifies the top-level and target-frame origins in the browser process and again in the broker, fills in the top frame's isolated world inside an exclusive protected operation, and returns sanitized status only. During the operation and a cooldown every other automation command on the tab except `page.inspect` is refused; afterwards filled fields stay redacted, `page.evaluate` is refused on the filled document and observation is refused if the page reveals or copies the secret into a plain field. The authorized site's own scripts can read the filled value (inherent). Not a defense against malware running as the same user or a compromised Weft process; no independent review yet.
- Payments ([ADR-019](decisions/019-payment-authorization.md)): `payments.propose` has Weft read the checkout itself (browser-verified top-level and checkout-frame origins, rendered totals, currency and recurrence wording, pay-control label) and queues one approval bound to a fingerprint of every term; the person approves it once on a dedicated payment card. `payments.submit` (class `payment`) re-reads the checkout immediately before clicking and refuses `terms_changed`/`merchant_changed`, voiding the approval; the attempt is committed before the click, one approval allows at most one attempt, and an interrupted attempt becomes `uncertain` until a person reconciles it. Card details are a `payment_card` vault entry filled through the protected-fill path with its own approval; filling never submits. Payment records live in `<profile>/payments`, outside workspace exports and backups.

## Section details

### 1–3: Purpose, outcomes, principles

**Status:** Partial.

Persistent project organization, shared commands, user-selected text models, human-visible tab ownership, and portable local project exports. Task continuity (ADR-016), enforced authority (ADR-005), credential brokerage (ADR-017, not independently reviewed) and payment authorization (ADR-019, not validated with real merchants) are implemented; hosted sync, collaboration and remote operation are deliberately out of scope (ADR-002).

### 4.1: Main interface

**Status:** Implemented, bounded.

Workspace rail/sidebar; native browsing region; navigation/address/tab controls; optional two-tab split with a saved focused pane; tab groups (named colors shown as text, collapsible, accessible group markup) and a tab quick switcher (Ctrl+Shift+A) with ownership, group, task and suspension labels; overview with a "Continue where you left off" panel (pinned resources, blockers, open handoffs), materials, context, tasks, conversations, artifacts, activity; collapsible chat/sidebar; command search/desk; settings, privacy, downloads. New installations start with one empty workspace rather than fabricated project data.

### 4.2: Everyday browsing

**Status:** Partial.

Back/forward/reload/stop, page find, zoom, downloads/cancellation, native file input, PDF generation, pinned tabs, common shortcuts, page tabs, stored session restoration. Dedicated history/bookmark views and commands are available; history retains up to 1,000 sanitized visits per workspace and bookmarks use pinned website materials. Unpacked Manifest V3 extensions can be installed per workspace by a person with explicit host grants, an audited permission allowlist (`storage`, `scripting`, `tabs`), hash pinning and revocation ([ADR-007](decisions/007-extension-compatibility.md)); no Web Store/CRX install, extension toolbar/options UI, optional permissions or Manifest V2. Human-only browsing-data import of bookmarks and history from Chromium-family profiles (`Bookmarks`, copied `History` SQLite), Firefox (`places.sqlite`, containers listed) and Netscape bookmark HTML with a preview of profiles, containers, duplicates, unsupported fields and never-imported data (passwords, cookies, sessions, autofill, payment data); the import must match the previewed digest ([ADR-015](decisions/015-headless-resume-and-resource-scheduling.md)). Tab groups and `tabs.search`. Idle and memory-pressure tab suspension (below, 21.1). Fixture-tested only; Safari and real browser profiles were not exercised.

### 4.3: Overview

**Status:** Implemented, bounded.

Actual materials, captures, tasks, blockers, and direct links; no invented activity. Pinned materials are prioritized. A per-workspace resume record (`resume.get`/`resume.save`) keeps the last section, active tab, split pane and focused pane, panel layout and pinned resources; continuation links to blocked/waiting tasks, open tasks and handoffs are recomputed from current records, and missing targets are reported. The window reopens the saved view and shows fixed restore disclosures.

### 5.1: Workspace records

**Status:** Implemented, bounded.

Stable IDs, names/descriptions/icons/colors/timestamps; create, edit, duplicate, switch, archive, restore, export, delete. Copies contain project records and stored content; browser sessions and model credentials are excluded. Imported/copied rules and workflows require review before enabling.

### 5.2: Isolation and sharing

**Status:** Implemented, bounded.

Separate project associations and separate Chromium storage partitions. Client tokens are restricted to granted workspaces; more than one workspace requires an explicit cross-workspace grant, and a tab's source workspace is checked when moving tabs. Shared context collections (#21, [ADR-013](decisions/013-shared-context-sources-and-provenance.md)): an owner workspace, items, participating workspaces with read/write roles, attributable history and revocation; only a person creates, grants, shares items or revokes. People, internal models (attachments and the search tool) and agents meet one record boundary; shared writes need revision checks and revocation applies to the next command. Context sharing never shares sessions: no shared browser container exists (decided in ADR-013) and a real Chromium test keeps cookies/localStorage isolated with a collection shared. No multi-user access controls.

### 5.3: Persistence

**Status:** Implemented, bounded.

Tab URLs/titles/pin/version/workspace/group (suspended tabs with scroll and zoom, restored unloaded), tab groups, per-workspace resume records, materials, context, task checkpoints, conversations, policies, workflows, artifacts, activity, and settings survive reopening. Restored pages reload; unsent form values and arbitrary live JavaScript state are not serialized.

### 6.1: Materials

**Status:** Implemented, bounded.

Editable notes with content revisions; website references; copied files up to 10 MiB with SHA-256, filename, MIME metadata, and download. Linked files and folders chosen by a person (native picker) record real path, size, mtime, inode and SHA-256/manifest hash; checks report available, changed, moved (found by inode or hash nearby), missing or inaccessible; refresh records source versions; relink is human-only. Agents read linked content only through `sources.read` (bounded, inside the linked root, traversal and symlink escapes refused, Weft's own profile never reachable) and never see the local path. A person chooses linked reference or managed copy. Service references use an adapter contract with a generic HTTP(S) adapter: explicit access status, refresh times, cached versions versus live content, conditional refresh, no redirects, OS-protected credentials and withheld content after revoked access. Status checks are on demand or scheduled; there is no filesystem watcher or OAuth connector.

### 6.2: Context categories

**Status:** Implemented, bounded.

Confirmed facts, findings, questions, instructions, and decisions with sources, revisions and per-revision provenance (`origin`: actor, kind, model, provider, tool call, conversation, capture; set from the authenticated caller, human authorship cannot be claimed by automation). Automation cannot create/edit trusted categories; agents propose findings (`context.propose`) and `context.promote` (action class `trusted_context`) needs a person, or a human approval for the agent once or standing (task-scoped for task-bound grants); autonomy levels and record/page text never authorize it. Promotion creates a new trusted record and keeps the finding.

### 6.3: Freshness and conflict

**Status:** Implemented, bounded.

Timestamps, optimistic revision checks, preserved revisions and versioned artifacts. Exact citations pin a capture version with a TextQuoteSelector, a record revision or a linked/service source hash; quotes re-anchor in newer versions after NFKC/ligature/typography/whitespace normalization and are marked verified, reanchored, stale or unverified (unknown targets never reject the record). `citations.check`, `freshness.check` and opt-in scheduled checks detect material changes locally and open `source_changed` conflicts; conflicts can also record contradictions or a conflicting edit. The GUI inspects subjects side by side and resolves attributably (keep both, choose, merge, dismiss) without rewriting originals. Format-2 export/import remaps citations, provenance (as claims), proposals, conflicts and collections and recomputes citation statuses. Previous bytes of a changed linked file are not preserved (hashes are); semantic contradictions are not detected automatically.

### 7.1–7.3: Ownership, handoff, multiple agents

**Status:** Partial.

Explicit control modes (you drive / assist / agent drives, human-only `tabs.setControlMode`), claim/release/takeover, navigation versions and a per-actor current-state inspection requirement before automation input. Persisted handoff records (`handoffs.create/list/get/accept/complete`) hold objective, completed actions, findings, exact evidence (artifact versions, record revisions, snapshot/capture IDs, sanitized URLs), blocker, next step and tab URL/version state; secret-like values are refused (best-effort pattern and key screening). Accepting requires re-inspection. Per-tab input is serialized with a configurable FIFO queue and optional exclusive (lease-required) mode; activity, queue and last control boundary are shown in tab state and the GUI. Takeovers report in-flight actions as not cancellable and are recorded as handoffs. Runtime tasks hand off through `handoffs.create` and wait until the handoff is completed (ADR-016). Settings → Agent input sets shared/exclusive input and the per-tab queue limit and wait (`settings.update` `automation`). The shown page carries a persistent ownership badge and a frame that only Weft draws (dashed while an agent drives, a 600 ms border pulse on a change of controller, removed under reduced motion); sidebar tabs show Working/Agent drives/Assist/waiting badges with distinct marker shapes; split view shows pane headers, a divider and a focused-pane frame.

### 7.4: Headed/headless

**Status:** Implemented, bounded (Linux/Xvfb verified).

`--headless`/`WEFT_HEADLESS=1` runs the same profile, hidden GUI renderer, policies and command catalog with pages rendered offscreen, so reads, snapshots and captures work without a visible window. Launching Weft again (single-instance handoff), `weft attach` or `display.show` shows the window without restart; human-only `display.hide` or closing a headless-started window detaches. Pages reload when they move between offscreen and on-screen rendering; transitions, reloaded tabs and lost unsaved input are recorded and shown. Pending approvals, and a locked encrypted profile that needs a person to attach and unlock, are reported by `display.status` and on stdout. Linux needs a display server (desktop or Xvfb): `--ozone-platform=headless` sizes windows at 1×1 and is unsupported. macOS/Windows not exercised. See ADR-015.

### 8.1: Tasks

**Status:** Implemented, bounded.

Objective, assignee, progress, evidence/output/material/tab references, checkpoint, next step, blocker and an executable plan (command, model, review and handoff steps). One phase vocabulary for tasks, workflow runs and model turns (queued, running, waiting_on_human, paused, completed, failed, cancelled, uncertain) with a transition table; every transition is stored on the record with actor and reason and mirrored in the activity log; legacy `waiting` records are normalized. Hand-tracked records still change state directly; runtime tasks only through the runtime. Results report staleness when the materials, workflow, model or plan that produced them changed. See [ADR-016](decisions/016-durable-task-runtime.md).

### 8.2: Task execution controls

**Status:** Implemented, bounded.

`src/task-runtime.js` executes plans through the shared dispatcher as the task's bound identity (built-in runner at a person-chosen autonomy level, the agent's own grant, or the automation token), so grants, approvals and emergency stop gate every step. Start, pause, continue, cancel, redirect (objective, model, unstarted steps), human-only reassign, review checkpoints (approve/reject/edit), handoff steps and model steps with the provider's disclosure rules. Operation records are committed before each step (record writes use store request IDs); expired grants pause with a blocker; approvals resume the task when decided. Emergency stop schedules nothing new and reports already-submitted steps. A startup sweep pauses interrupted local work and marks attempted external work `uncertain`; `tasks.reconcile` records a human or recorded-lookup determination and `tasks.retryStep` repeats uncertain work only with `confirmDuplicateRisk: true` from a person. No reconciler exists for page actions; `payments.submit` steps use the payment reconciler (virtual-card transaction lookup, otherwise a person decides; ADR-019).

### 8.3: Reusable workflows

**Status:** Implemented, bounded.

Typed parameters with `{{name}}` substitution, required materials, allowed sites enforced per step, credential references resolved through the credential broker (usable only as `credentials.fill` ids), review checkpoints, expected-output confirmation, sensitive parameters held only in memory. `workflows.run` executes as a runtime task under current grants; `workflows.validate` reports problems first. Invalidated steps (missing selector/ref, URL assumption, allowed-site exit) pause before input. Imported, agent-written or agent-edited workflows are inactive until a person reviews them. Human-only recording captures navigation, Weft commands and trusted in-page clicks/field changes from an isolated world as selectors and parameters, never values; password fields become `credentials.fill` steps. Not captured: typed keystrokes, drag and drop, cross-origin frames, closed shadow roots.

### 9: Models and chat

**Status:** Implemented, bounded.

OpenAI-compatible, Anthropic and Ollama-native adapters with SSE/NDJSON streaming, normalized finish reasons and in-band error frames treated as failures; a defined turn lifecycle (cancel, originating disconnect, emergency stop and admission latch keep partial replies marked interrupted; length/deadline stops are continuable; runtime errors are failed turn manifests, never replies) with first-token, idle and total deadlines; deltas to the GUI over trusted IPC and to API clients over SSE with resumable turn streams. Typed attachments (passages, tab snapshots, materials, context, tasks, exact artifact versions) with per-item delivery disclosure and exclusion; per-model capability records from configuration, endpoint probing (`models.probe`) or adapter defaults; context-window planning that omits oldest history (no summarization) while originals stay intact; typed `unsupported_capability` outcomes; bounded PNG image transport; explicit vision fallback with scoped data and provenance; provider-reported usage, endpoint locality and configured-price cost estimates. Editable endpoints, OS-encrypted keys/environment references, itemized cloud consent, local-only restrictions, persisted per-turn manifests and opt-in read-only tools remain. `chat.send` is a `cloud_spend` action under the shared authority gate (client grants need that class; approvals apply), and every destination decision, primary and vision-fallback request and turn outcome is recorded in durable activity without content; the internal read tools dispatch through the same gate. Not provided: write tools, Anthropic/Ollama tool use, model-generated summarization of omitted history, tokenizer-exact budgeting, non-PNG images, or live validation against real provider accounts.

### 10: Shared command architecture

**Status:** Partial.

Canonical schema, GUI/CLI/MCP/REST dispatch, discovery, generated authenticated OpenAPI 3.1, authenticated live SSE metadata, loopback API, origin rejection, structured JSON errors, shared state. Typed outcomes, actionable errors, stable CLI exits, normalization, generated reference, grouped MCP, per-client identities/scopes/revocation and typed authority denials/approval requests (`error.details.authority`) are implemented. Built-in plugin commands join the catalog as `plugin.<name>.<operation>`; plugins reach core only through named hooks ([plugins](PLUGINS.md)). `activity.list` has cursor pagination, and every other large collection accepts an additive `page: {limit, cursor}` returning `{items, nextCursor, total}` with stable opaque keyset cursors (ADR 018). Every outcome carries a stable `status` (succeeded, partial, blocked, approval_required, stale_state, conflict, unsupported, invalid, cancelled, timed_out, failed) derived from one table and contract-tested across GUI IPC, REST, CLI and MCP for every error code, plus the authenticated `request` linkage (API version, requestId, actor, client, task, deadline). Caller deadlines (REST header/body field, CLI `--deadline-ms`, MCP `deadlineMs`) abort through the shared signal and return `deadline_exceeded` stating whether execution started and whether it rolled back, stopped or is uncertain. `weft.capabilities`/`GET /v1/capabilities` publishes API version, catalog hash, outcome table, limits and features; MCP serves read-only resources (guidance, command reference, capabilities, scoped workspace records). Chunked uploads (`transfers.*`, SHA-256 verified) and streamed downloads (`transfers.read`, `GET /v1/download`) move content beyond the 1 MiB request cap; package uploads stage `workspaces.exportPackage` folders whose import stays human-only. Request-ID idempotency for record mutations (replay/conflict, per-caller scope, bounded retention), atomic record batches authorized per contained command through the shared gate (one exact approval for the whole batch when needed), and dry runs are implemented through the shared catalog. Authenticated SSE event ids with bounded in-memory `Last-Event-ID` replay and explicit gap frames, and the same retained log through `events.list` for CLI/MCP; task, artifact, navigation, handoff, policy, workspace and approval changes are typed metadata events. SSE streaming of command progress with originating-disconnect cancellation; resumable per-turn streams. No remote TLS deployment, persisted event history across restarts, upload sessions that survive a restart, or validation with external MCP clients' resource browsers.

### 11: Page understanding/screenshots

**Status:** Partial.

Readable page text/links, HTML, browser state/version, `page.snapshot` (DOM-derived semantic tree with roles, accessible names, states, boxes, frame-scoped stable refs and a coverage report for inaccessible cross-origin frames, redacted fields, lazy/busy/virtualized/opaque/hidden content and truncation), ref- or selector-based click/fill with element fingerprint checks, permission-gated coordinate/key input with geometry validation, viewport/full-page/element/region PNG with crop and resolution limits and complete capture metadata, sensitive-field masking, and PDF. MCP returns screenshot image content. Chromium's platform accessibility tree, closed shadow roots and cross-origin frame contents are not represented; full-page capture cannot guarantee lazy-loaded or virtualized content.

### 12: Permanent artifacts

**Status:** Partial.

Durable offline text/PNG bundles and resource archives (ADR-012: Chromium MHTML split into content-addressed resource components with a manifest of URL, MIME type, size, SHA-256 and status, explicit failed/missing/script/oversized entries, sensitive form values removed) stored as verified component files; immutable capture versions with bounded readiness/duration and capture metadata (original/final URL, timing, viewport, state changes, request failures, virtualization/lazy/frame coverage, incomplete reasons); `artifacts.verify`; `artifacts.compare` (text, resource and pixel diffs) in the GUI and catalog; a script-free, network-free offline preview; previous-version linkage, annotations, exact-version reads, ranked full-text search citing exact versions and lossless export/import including archives. Sanitized derivative versions (`artifacts.redact`: text spans, URL/title and re-encoded PNG regions, preview before saving) with separate human access (`artifacts.setAccess`) and retention (`artifacts.purgeContent`) decisions and pattern detection assistance. Restricted originals stay withheld from agents and model readers in shared-collection reads, and never supply citation anchors, selectors or re-anchoring text (a sanitized derivative is used, or the citation is reported unverified); automation archive capture is refused on a tab in a protected login operation. No interactive replay of scripts, redaction of archived HTML, OCR of images, independent timestamp authenticity or complete PII detection.

### 13: Credential broker/payments

**Status:** Partial.

Credentials (13.1–13.4, 13.6): isolated broker process, local AES-256-GCM vault with a `safeStorage`-wrapped key (basic_text refused), optional 1Password CLI adapter (fake-CLI tested only), purpose-bound references with exact origins/frames, expiry, revocation and masked identifiers, GUI-only creation through a browser-owned entry window, once-only approval or task grant per use, exclusive protected login with observation suppression, residue protections and sanitized results ([ADR-017](decisions/017-credential-broker-and-protected-login.md)). Independent security review has not been performed, so isolation is not asserted; no Bitwarden/KeePassXC adapter; no vault rollback detection. Payments (13.5; [ADR-019](decisions/019-payment-authorization.md)): browser-owned approvals bound to the merchant origin, checkout frame, exact checkout destination, amount ceiling, itemized total/tax/shipping read from the page, ISO 4217 currency, recurrence and cap, actor, purpose and task; revalidation immediately before the click with `terms_changed`/`merchant_changed` refusals that void the approval; card filling (`payment_card` vault entries, `credential_use`) separate from purchase authorization (`payment`); attempts recorded before the click, uncertain outcomes reconciled through a registered payment reconciler; cancellation voids unsubmitted payments and never claims refunds; an optional virtual-card issuer adapter (off by default) with clear `unsupported` outcomes. Not validated with real merchants, payment processors (3-D Secure, wallets, split card frames beyond the fixture) or a real issuer account. Provider API-key storage remains separate.

### 14: Permission and trust model

**Status:** Partial.

One authority gate in the shared dispatcher for every non-human caller, including internal model tools. Action classes (observation, local work, external changes, code execution, model egress, once-only bulk export/credential/payment/unclassified, trusted-context promotion that only explicit human approval admits, human-only administration) and autonomy levels (observe, assist, scoped, autonomous) with per-workspace ceilings. External changes (form submissions, messages, account changes via click/fill/script) need a standing grant or a browser-owned approval; once-only classes need an exact approval each time. Approvals are bound to an exact command/argument/actor/target fingerprint, expire, can be one-time or standing (optionally task-bound) and are resolved only in the GUI; page/artifact text and command arguments cannot approve or widen grants. Purpose/destination/data-class grants and itemized model egress acknowledgement are implemented; the `restricted_original` data class is never granted by default and every agent read of a restricted original needs an exact one-time approval (no standing approvals or autonomy). The credential broker (ADR-017) and payment authorization (ADR-019) use the once-only `credential_use` and `payment` classes; payment approvals are bound to the payment's terms rather than to a tab version, and a changed checkout invalidates them (a new approval status, never given back). Emergency stop revokes tab leases, stops loads/downloads, pauses runtime tasks (reporting already-submitted steps) and hand-tracked running records, and aborts model requests; a shared stopped-state latch rejects subsequent automation until human resume, even if task persistence fails. Already executed external actions cannot be undone. Destination grants do not stop a redirect mid-navigation; later commands on the redirected page are refused.

### 15: Malicious content/downloads

**Status:** Partial.

Page sandbox, unsupported navigation schemes denied, all web permission requests denied and counted per tab. External application/protocol launches become pending browser-owned requests with source page, frame and scheme; only a person can approve one once, and abuse-prone schemes are refused (ADR-009). Popups need input in their tab. Unsolicited downloads are cancelled and listed with source page, file type and redirect hosts; repeats collapse, bursts are suppressed, and a person can approve one exact retry. Downloads stay in a separate folder, are never opened, get SHA-256, OS origin metadata where available (Windows Mark-of-the-Web, macOS quarantine, Linux xattr when `setfattr` exists) and an optional human-configured local scanner (`unscanned`/`clean`/`infected`/`scan-failed`). Hash-pinned offline threat lists and an optional, off-by-default Safe Browsing v4-compatible hash-prefix provider produce security findings separate from preference rules, with staleness. Windows/macOS metadata, a real scanner and a live provider are unverified here; no exploit prevention is claimed.

### 16: Cookies and storage

**Status:** Implemented, bounded.

Workspace partition isolation, human-only cookie administration and clearing, plus browser-owned modes per site and per workspace default: block (header removal plus opaque-origin CSP sandbox so Chromium refuses script cookies, Web Storage, IndexedDB, Cache Storage and service workers), session (write-ahead journal; erased at clean exit or at the next startup after a crash, before tabs restore) and remember. Cross-site `SameSite=None` cookie headers are removed by default using an approximate registrable domain, judged by the requesting document and the top page. A quiet site-controls indicator counts blocked activity. Published coverage matrix and limitations in `storage.policy` and ADR-008. No necessary-versus-tracker classification, fingerprinting prevention or server-side session revocation.

### 17: Personal site rules

**Status:** Implemented, bounded.

Hostname/domain-boundary normalization, optional path, workspace/global scope, reasons, notes, evidence links, creator, revision history with changed fields, review dates and a human review action, enabled state, navigation/connection blocking and human-only exact-destination overrides. `siteRules.explain` (and the GUI “Why?” dialog) lists every matching rule, security finding and exception in explicit precedence order with IDN/punycode details; blocked agent actions return structured `site_blocked` results. Engine-path coverage (redirects, frames, workers, sockets, popups, speculative loads) is tested and uncovered paths are documented in BROWSER-SAFETY-AUDIT.md. Chromium request interception is not a host firewall and cannot constrain an external agent's own networking.

### 18: Community lists

**Status:** Implemented for the local client and file-based publication; fixtures only.

Human-only signed subscriptions (Ed25519 key pinned at subscribe time, rotation statement, monotonic versions, rollback only on explicit human action), private-group/public label/warn/block modes, digest-confirmed previews of added/removed/changed entries and newly blocked domains, rollback, unsubscribe, visible per-site exceptions, opt-in scheduled fetch that only stores a pending update, strict entry schema (claims, sources, submitter/reviewers, entity vs domain, fact vs opinion, dates, status, revision history), file-based governance (roles, N-reviewer acceptance, corrections, disputes, appeals, stale review, rate/size limits) with `scripts/community-list.js`, and all-match provenance/precedence via `lists.matches`. Legacy hash-pinned installs remain. See ADR-004. No Weft-hosted moderation service, authenticated member identities, transparency log or independent security review; never exercised against a real hosted list. A Settings → Community site lists screen subscribes (publisher key fingerprint and full diff shown, acknowledgement and confirmed digest required), reviews pending or file-supplied updates, changes mode/reviewer floor/source/scheduled checks, adds and removes exceptions, shows all matches for an address, rolls back and unsubscribes.

### 19: Activity and audit

**Status:** Implemented, bounded.

Append-only hash-chained activity log records commands (all writes and non-human reads), permission decisions and denials, approval requests/decisions, grant and policy changes, model destination decisions, site-rule/download blocks, overrides and artifact creation, with actor, client, task, workspace, tab, target and version links. Outcomes are labelled attempted, completed, failed, denied, pending approval, partial, externally uncertain or cancelled, with irreversible/external flags; history is not proof of external success. Arguments are minimized (IDs, counts, URLs without credentials/query/fragment) and secret-named fields dropped. Configurable age/count retention (default 90 days/20,000 entries) also prunes ordinary workspace activity and never removes records or artifacts. `activity.verify` gives tamper evidence for the retained window; it is not tamper-proof against a process that can rewrite the profile. GUI activity view has type/outcome filters, cursor paging, inspectable detail and retention/integrity controls.

### 20: Data model/recovery

**Status:** Partial.

Transactional SQLite metadata (WAL, schema-versioned append-only migrations, per-command transactions), content-addressed verified component files, process ownership lock, external-writer and file-replacement detection, lossless one-time migration from the version 1/2 JSON store with the original preserved, recovery of interrupted migrations, preservation of corrupt/newer stores, orphan-component recovery, verified automatic (daily, latest five) and manual backups, journaled restore with preserved originals and offline CLI recovery, lossless format-2 export/import with lossy-mapping reports, package transfer for large projects, secret-key guards, optional export residue scanning, sync-folder/conflict warnings and disabled imported policies/workflows. Optional per-workspace embeddings (human-enabled, existing local connection, no model download, float32 vectors with exact cosine search up to 20,000 per workspace, incremental queue, re-embedding on model change) fused with BM25 by reciprocal rank, with coverage and verified-absence reporting (ADR 018). Opt-in workspace encryption at rest (ADR 014): AES-256-GCM sealed records, settings, request results and keyed-name components, an in-memory-only search index, a profile key wrapped by the OS key store (`basic_text` refused), a one-time recovery key and an optional scrypt passphrase; human-only lock/unlock with typed `locked` outcomes on every surface; wrapping and resumable data-key rotation; crash-safe in-place enable/disable; encrypted backups carrying their keyring; plaintext exports only with explicit acknowledgement. Real Keychain/DPAPI/secret-service backends are unverified. In an encrypted profile embedding vectors are sealed at rest per chunk (an index-derived key, keyed digests), so unlocking only decrypts and never re-sends unchanged text; upload parts stay in memory. No off-device backup, sync, approximate vector index or collaboration. Handoff records, storage modes and community subscriptions live in the same database. See ADR 011.

### 21.1: Reliability/performance

**Status:** Partial.

Bounded API/provider request sizes, provider response/context/time limits, serialized store mutations, per-command transactions that write only changed rows, optimistic revisions, and screenshot timeouts. Separate performance budgets cover 10k-record writes, ranked search, export/import, a capture-heavy store (500 captures, ~60 MiB of components) where metadata edits are asserted not to rewrite components, catalog generation and exact cosine search at the 20,000-vector limit. Full-text index rebuilds (index version change, encrypted in-memory index after unlock) run as bounded background batches between commands with progress, `search.indexing` pause/resume, `indexing` events and partial search results with coverage; a plaintext rebuild resumes after restart. Measured real-Electron targets for GUI first render, navigation, input, scroll, memory and CPU with concurrent agents (`perf/responsiveness.js`, CI budgets in `test/responsiveness.test.js`); all numbers are Linux/Xvfb software rendering, not real hardware or other platforms.

### 21.3: Privacy

**Status:** Partial.

Local project storage, user-selected model destination/context, no telemetry or crash reporting implementation (any future crash reporting must be opt-in, separate from content and redacted; see ADR-005), no silent model fallback, provider keys excluded from project exports. Activity entries exclude secrets and minimize personal data (identifier-shaped values are kept only in id fields; names and free text become a character count; service, endpoint and list URLs keep only their origin). Opt-in workspace encryption protects project data at rest from disk theft, other accounts and copied backups, not from software running as the user while unlocked (ADR 014). Client data-class and destination grants limit what agents can read and where they can act. Captures can be redacted into sanitized derivatives whose restricted originals are withheld from agents, model attachments, search and default exports (ADR-012); detection is pattern assistance only. Free-form notes, tags, annotations and unreviewed captures can still contain secrets or personal data; export is not a content redaction guarantee. No comprehensive outbound-data classifier.

## Data handling and recovery limits

Unless a person turns on workspace encryption (Settings > Encryption, ADR 014), project metadata is stored in `workspace-data/workspace.sqlite` (with its WAL) beneath Electron's user-data directory, and capture/file bytes in `workspace-data/components/`. With it on, records, settings, request results, components, embedding vectors, payment records and later backups are sealed with AES-256-GCM and the search index exists only in memory (rebuilt in the background after unlock); identifiers, counts, sizes, the activity log, policy files and Chromium partitions stay plaintext, and plaintext copies made earlier are listed until removed. Model connection metadata and encrypted key blobs use a separate file. Payment records (terms, approvals, attempts and outcomes; never card numbers) are in `<user data>/payments/payments.json` with the optional card-issuer key wrapped by OS-protected storage; like the credential vault they sit outside `workspace-data`, so workspace exports and backups do not include them; with workspace encryption on they are sealed with the same keys and unreadable while locked (ADR 014 coverage table, ADR 019); service-reference credentials are OS-encrypted blobs in `workspace-data/service-credentials.json`, which is not part of exports or backups. Linked files and folders stay where they are; Weft stores their path and hashes, not their bytes. Chromium session data resides in its own partition storage. Browser security state uses separate small files beside the project store: `temporary-storage-journal.json` (origins to erase), `threat-intel.json` (installed lists and provider state; no API key) and `download-safety.json` (scanner configuration). Storage modes and handoff records are kept in the project database; storage modes are excluded from exports. Without workspace encryption the database, components, search index, backups and recovery copies are **not encrypted at rest**; with it on, the plaintext categories listed above remain, and Chromium partitions and swap are never covered. Files are written with restrictive requested permissions where supported, but host filesystem/OS permissions remain relevant.

Each stored material is limited to 10 MiB, each PNG capture to 20 MiB, each component file to 32 MiB and each record document to 64 MiB; the project as a whole is bounded by disk space rather than a fixed store cap. Metadata changes rewrite only the changed rows; component files are never rewritten. JSON imports are limited to 100 MiB (the GUI accepts files below 50 MiB) and REST requests to 1 MiB, so larger projects use human-only package folders (`workspaces.exportPackage`/`workspaces.importPackage`), and agents move single large files with verified chunked transfer sessions (`transfers.*`, 512 KiB chunks; stored-content limits still apply). One Weft process owns a profile at a time; concurrent independent writers are refused rather than merged.

Resource archives (ADR-012) store each resource as its own component (8 MiB per resource by default, at most 32 MiB; 64 MiB per archive) and list everything else with an explicit status; MHTML is serialized to a temporary `capture-temp/` folder in the profile and removed afterwards. Archive hashes show bytes are unchanged since capture, not what a site served or when. Restricting an original removes it from the search index with FTS5 secure-delete and truncates the WAL; purging deletes its component files from the profile but cannot guarantee physical erasure, and earlier backups and exports still contain it. Redaction never rewrites artifact notes, tags or annotations, does not redact archived HTML and does not detect text inside images.

Export excludes configured provider keys, Chromium sessions/cookies, model settings, and global site rules. URL metadata removes known sensitive parameter names and fragments. This is not comprehensive secret detection: user-authored notes, URL path segments, ordinary query values, copied files, transcripts, and screenshots may contain sensitive information. Inspect exported content before sharing it. Optional exact-term residue scanning reports found/clean/unverifiable and treats PNGs/unsupported binary formats as unverifiable; it is not automatic redaction. See [local storage and export safety](STORAGE-SAFETY.md) for lock recovery, schema upgrades, conflict warnings, and tested limits.

An import never writes a path from its input. Stored file names are reduced to basenames; source HTML is retained as plain text; PNG base64 is normalized and recorded component hashes must match. Import rejects malformed supported fields and rolls back project state on failure. It creates new IDs and resets site rules/workflows to inactive, and its report lists every lossy mapping. Project duplication uses the same import pathway. The application keeps verified automatic and manual local backups; restore verifies first and preserves the replaced data under `recovery/`, and `weft store restore` works offline when the database cannot be opened. Backups share the profile's disk. Corrupt, newer or conflicting stores are preserved unchanged. See [local storage safety](STORAGE-SAFETY.md).

## Distribution and updates

Policy: [ADR-010](decisions/010-distribution-and-updates.md); procedure, trust roots and support policy: [RELEASING.md](RELEASING.md).

- **Packaging:** `electron-builder.config.cjs` builds Windows NSIS x64, macOS dmg/zip (arm64, x64) and Linux AppImage/deb (x64). The Windows installer is assisted, per-user by default, with brand bitmaps drawn with Vixl (`scripts/graphics/installer.py`, encoded by `scripts/generate-installer-art.js` and checked byte-for-byte by tests) and `packaging/installer.nsh` text. Upgrades never touch user data; uninstall keeps the `weft` profile unless the person ticks and confirms deletion. Packaged builds pin the profile folder to `appData/weft`, the same as source runs. Verified: Linux AppImage/deb build, packaged AppImage launch smoke test; NSIS installer and uninstaller scripts compile with makensis on Linux. CI and the release workflow build the real unsigned installer on `windows-latest` and run `scripts/release/windows-install-check.ps1` (silent install, registry entry and shortcuts, installed-app smoke test, reinstall, silent uninstall keeping workspace data), which passes on the `windows-latest` runner. The unsigned macOS CI check builds dmg/zip for arm64 and x64, verifies their manifests and launches the native arm64 app on `macos-latest`. Not verified: interactive installer pages on Windows, launching the x64 macOS app on Intel hardware, signing/notarization.
- **Updater (`src/updater.js`):** `update.status` (local read; also available to scoped read clients) and human-only `update.check`, `update.install`, `update.rollback`, `update.configure` in the shared catalog; GUI Settings > Updates shows version, channel, install type, kill switch, last check, staged update, verification and signature status, health and rollback. Requests go only to the compiled `jxburros/Weft` releases URL and allowlisted GitHub release hosts through a cookie-less Electron session; the manifest must be strict electron-builder `latest*.yml`, stable, newer, and match its release tag. Files are size/SHA-512-verified while streaming and again before install; Windows pins the Authenticode publisher of a signed installation. Background checks are off by default, at most daily and only stage. Source runs have no transport; `WEFT_DISABLE_UPDATES` stops all update traffic and installs.
- **Activation and rollback:** Windows hands off to the visible installer (`--updated`); AppImage is replaced by copy-verify-rename and relaunched; macOS dmg and `.deb` are opened for a visible manual install and reported as `handed_off_manual`. The new version must pass a health check (GUI loaded, API listening, store open) within two launches; otherwise it is marked failed, AppImage restores the retained previous file automatically, Windows offers a retained verified previous installer when one exists, and other platforms show manual guidance. A crash before Weft's JavaScript starts cannot be detected directly.
- **Release workflow:** Packaging removes empty certificate-link inputs from missing Actions secrets, verifies each platform's manifests even on dry runs, and lets all platform jobs finish after a failure. Manual dry runs on tags cannot publish. CI builds macOS dmg/zip for both architectures and smoke-tests the runner's native app.

## API contract and live events

Authenticated `GET /v1/openapi.json` publishes an OpenAPI 3.1 document generated from every canonical command's JSON schema. `POST /v1/execute` uses a discriminated command envelope; the published alternatives preserve each command's input requirements. Human-only operations remain listed for discovery but cannot be authorized by an automation token. Gate refusals return 403 with `error.details.authority`; approval requests return 403 `approval_required` (CLI exit 5) with an `approvalId`.

Authenticated `GET /v1/events` provides live server-sent events. Supply the bearer token in the HTTP authorization header; URL tokens and browser-origin EventSource access are unsupported. Events use a strict metadata allowlist: event type, known command, human/automation/scoped-client actor, success/failure, stable workspace/target IDs, tab ID, and state version. They do not contain command arguments, results, errors, page URLs/titles, provider messages, or screenshots. Gate refusals and approval requests appear with status `blocked`. The event stream is not an audit transcript (use `activity.list`) or proof of an external action's success. Scoped clients receive only authorized workspace events; expiry/revocation ends streams. Each event has an SSE id; reconnecting with `Last-Event-ID` replays retained later events (in memory only: 1,000 events, 1 MiB, 15 minutes) under the same allowlist and scope, preceded by an `event: gap` frame when events expired, the process restarted or the id is unknown. Consumers should read current state after a gap. Model turn progress uses separate authenticated turn streams documented in [agent integration](AGENT-INTEGRATION.md).

Events also cover task, artifact, navigation (committed, in-page, blocked), policy, workspace and approval changes as metadata only; the application shares one retained log between the stream and `events.list`, so CLI and MCP callers resume from the same ids.

The server limits concurrent event subscribers to 16, emits heartbeat comments, disconnects slow consumers, and unsubscribes closed connections. When the server is used without a shared application subscription callback, only commands executed through that server produce events.
