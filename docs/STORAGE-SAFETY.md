# Local storage and export safety

Verified against code: 2026-10-17. These safeguards cover the JSON store while the transactional-storage work in #25 remains open.

Weft holds `.workspace.lock` in the canonical profile data directory. Exclusive file creation prevents a second process from opening the store; services in the same process share ownership but retain independent disk stamps. Normal process exit or `WorkspaceService.close()` releases only the owned lock. Abrupt termination can leave a lock: close all processes using the profile, preserve a backup, and remove `.workspace.lock` only after checking that no writer remains. Weft never guesses that a PID or remote host is dead. Network filesystems and live cloud synchronization are unsupported.

Every save checks device/inode, timestamps, length, and SHA-256 against the last read/write. A changed or missing original causes `STORE_CONFLICT`; the pending command rolls back its in-memory records and preserves external bytes. Writes use an exclusive temporary file, file fsync, reread/JSON parsing and byte verification, a second conflict check, atomic rename, directory fsync where supported, and a final digest check. A directory-flush failure after rename reports `STORE_DURABILITY_UNCERTAIN`: the replacement may be present, so restart and inspect before retrying. These checks cannot eliminate the final race with a writer that ignores the lock; they do not turn JSON into a database or authorize simultaneous editing.

`src/migrations.js` contains append-only transitions. Version 1 to 2 makes browsing history an explicit collection. Migrations operate on a clone, preserve unknown fields, and validate store structure, IDs, active workspace and workspace ownership before writing. Original bytes are retained in a permission-restricted, fsynced `workspace-state.json.schema1-<sha256>.bak`. Newer schemas fail without replacement. Historical store and export fixtures live under `test/fixtures/schema-v*`; imports use the same version runner and reject unmapped relationships rather than silently deleting them. This migration backup is not an automatic backup service. Existing free-form citations and historical references are not fully validated/remapped (#27).

Secret-named keys (including nested ignored import fields), workflow parameter names such as `api_key`, and direct attempts to save secret-bearing structured data are rejected with `SECRET_FIELD`, without echoing values. This does not detect secrets written into ordinary prose. Existing files containing such keys are preserved and opening fails explicitly; review a copy and remove the sensitive fields before reopening.

`workspaces.export` optionally accepts `sensitiveTerms` (at most 100 nonempty strings of up to 200 characters) and returns `residueScan`. The scanner inspects serialized output, decoded JSON strings, note/capture text and UTF-8 text-file bytes. `found` means at least one exact, case-sensitive supplied term was found; `clean` means those terms were absent from the supported inspected data; `unverifiable` means at least one image, unsupported binary or undecodable text component remains. A `found` report still includes any unverifiable components. Only SHA-256 hashes of terms appear in the report. Screenshots are never declared clean through this scan. It does not perform OCR, unpack archives, redact content, or certify the absence of other secrets/PII.

Startup and snapshots report known Dropbox, OneDrive, Google Drive and iCloud paths, environment-configured sync roots, conflicted workspace copies and placeholder files. Warnings reach the startup log and `snapshot.storageWarnings` for the trusted GUI; workspace-scoped automation does not receive filenames. Copies are never merged, renamed or deleted. If only conflicted copies/placeholders exist, opening stops rather than creating a misleading empty project. Human review means preserving all copies, comparing them outside the live profile, and selecting/restoring a canonical file with Weft closed. Detection uses path/name heuristics and cannot identify every sync client or alternate naming convention.

Validation: `node --test test/storage-safety.test.js test/workspace.test.js` covers cross-process locks, stale readers, lock loss, external same-length edits, corrupted temporary writes, historical migrations/backup bytes, newer schemas, invalid relationships, secret guards, three scan outcomes, and preserved sync conflicts. Windows directory-fsync behavior and real sync-client races have not been exercised on this Linux runner.
